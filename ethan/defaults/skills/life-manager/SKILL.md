# Life Manager

> 时间线和定时任务管理由 `schedule-manager` 负责，本技能专注「记录 + 识别 + 提醒」。
> 数据统一写入**知识库**（`scene` 区分 `work`/`life`），后端可在 filesystem / Obsidian / external 间切换。

## 🚫 硬规则（必须遵守，不可绕过）

### R1：写知识库只用 knowledge_* 工具

所有 life-manager 技能产生的数据写入，必须通过 `knowledge_add` / `knowledge_edit` 完成。

- ❌ 禁止 `file_write` 直接写 markdown
- ❌ 禁止 `shell` 的 `mkdir` / `cat` / `echo`
- ❌ 禁止自己拼接 vault 路径——路径由后端管理
- ✅ 新建 → `knowledge_add(title, content, tags, scene, frontmatter)`
- ✅ 追加 → `knowledge_edit(source, content, mode="append", scene)`
- ✅ 整篇替换 → `knowledge_edit(source, content, mode="replace", scene, frontmatter)`

**判断标准**：只要写入的内容属于本技能管理的条目类型（见下方数据存储表），即使已经用 lark-cli / web_fetch 拉取了原文，写回时也必须走 knowledge_* 工具。

### R2：内容来自外部文档/链接时，frontmatter={"source": ...} 必传

凡是条目内容派生自外部网页/飞书文档/链接（用户提供了 URL，或你用 lark-cli / web_fetch 拉取过原文），调用 `knowledge_add` / `knowledge_edit` 时必须传 `frontmatter={"source": "{原始 URL}"}`。

- 固定字段（title/type/tags/created/updated）由后端自动管理，**不要**在 frontmatter 里重复传
- 可按需追加 `author` / `published` / `url` 等字段
- filesystem 后端会忽略 frontmatter，但参数仍要传（保持一致，后端切换时不丢字段）

### R3：scene 按场景区分

| 内容类型 | scene | 示例 |
|---|---|---|
| 团队/工作向记录 | `work` | 人员日志、项目进展、CR 周报、绩效草稿、工作沉淀 |
| 个人/生活向记录 | `life` | 健康记账、家庭事项、个人学习、生活提醒 |
| 不确定 | `work` | 默认 work，用户明确说生活类时切 life |

## ⚡ 快速路径（优先匹配，命中即执行，勿绕路）

### 「整理进 people」

**触发**：「把 xxx 整理进 people」「记到 people 里」

1. 从用户消息或上下文中提取 `{姓名}: {事件}` 列表
2. 对每个人，用 `knowledge_edit`（mode=append，scene="work"）追加到 `人员日志 - {姓名}`：
   ```
   ## {MM-DD}
   - {事件描述}（{HH:MM}）
   ```
   条目不存在时先 `knowledge_add` 创建（tags: `["people", "{姓名}"]`）
3. 回复确认：列出写入了哪些人、各写了什么

### 「业务进展 / 工作进展」

**触发**：「更新业务进展」「更新工作进展」或发送文档/链接要求更新进展。只要用户意图是"把某些人做的事/项目进展记录下来"，即使没精确命中 trigger 也走此路径。

1. 读取文档/上下文内容，提取**每个人做的最关键的事**（精简）
2. **写 people**：对每个人，用 `knowledge_edit`（scene="work"）追加到 `人员日志 - {姓名}`
3. **写 project**：用 `knowledge_edit`（scene="work"）追加到 `项目进展 - {业务名} - {项目名}`：
   ```markdown
   ## {YYYY-MM-DD}
   - {进展条目}（@{姓名}）
   ```
4. **同步触发定时信号识别**：进展中含时间节点（如"8.15 完成"）按下方「定时信号识别」处理
5. 回复确认：列出更新了哪些人、哪些项目

### 「工作沉淀整理 / 分类写入」

**触发**：「整理下 XX 的工作沉淀」「整理这个同事的沉淀，分类写入」「把这份文档按类别整理进来」

1. 拉取原文（飞书 docx 用 `lark-cli docs +fetch`；网页用 `web_fetch`）
2. 按内容结构分类（如：技术沉淀、项目复盘、方法论、踩坑总结、团队协作等，由内容决定）
3. **每一类创建一个独立的知识库条目**，用 `knowledge_add`（scene="work"）：
   - 标题：`{姓名}工作沉淀 - {分类名}`
   - tags：`["doc", "people", "{姓名}", "{分类名}"]`
   - frontmatter：`{"source": "{原始文档 URL}"}`（R2 必传）
   - 内容：
     ```markdown
     # {分类名}

     > 原文：{url}
     > 作者：{姓名}
     > 整理日期：{YYYY-MM-DD}

     {按内容结构组织，保留关键观点、数据、方法，去掉口水话}
     ```
4. **同时追加一条事件到 `人员日志 - {姓名}`**（mode=append，scene="work"）：
   ```
   ## {MM-DD}
   - [亮点] 整理了工作沉淀（{分类数} 个分类），原文：{url}（{HH:MM}）
   ```
5. 回复确认：列出创建了多少个分类条目、各自标题、原文链接已写入 front matter

### 「文档/链接收藏」

**触发**：用户发送文档链接、说「收藏这个」「存一下」，或 Agent 处理过程中解析了任何文档/链接时**自动追加收藏记录**。

1. 解析文档：提取标题、链接、一句话摘要、作者（可选）、日期
2. 判断归属业务（不确定用"未分类"）
3. 用 `knowledge_add`（scene 按内容判断，工作向 work / 生活向 life）创建收藏条目：
   - 标题：`文档收藏 - {文档标题}`
   - tags：`["doc", "{业务名}", "{分类}"]`
   - frontmatter：`{"source": "{url}"}`（R2 必传）
   - 内容：
     ```markdown
     - 链接：{url}
     - 一句话介绍：{摘要}
     - 作者：{作者}
     - 日期：{YYYY-MM-DD}
     ```

### 「定时信号识别」（核心能力）

**触发**：在任何对话/电话/妙记/文档/口述中识别到时间节点或待办信号。

**信号来源**（重要——别只盯对话文字）：
- 用户直接发的消息
- **电话/通话录音转文字**（用户说"刚才电话里说..."、"通话记录里提到..."）
- **飞书妙记/会议纪要**（用户转来 minute_token 或妙记链接）
- 拉取的飞书文档、网页内容
- 口述转写（语音消息、口头交代）

**信号类型**：
- 明确日期：「8.15 前完成」「下周五交付」「10 月底上线」
- 相对时间：「下周三」「三天后」「月底」「每周一」
- 周期性：「每天早上扫一下」「每周五汇总」「每月 15 号」
- 待办动词 + 时间：「提醒我下周三...」「记一下周五要...」「8.20 要去...」
- 隐式截止：「这个项目 8.15 上线」（隐含"到点要检查"）

**执行流程（先确认再创建）**：

1. **识别**：从用户消息或文档中抽取所有候选时间信号，每个信号提取：
   - `{时间表达式}`：原文表述（如"下周五"）
   - `{解析后的具体日期}`：解析成 `YYYY-MM-DD HH:MM`（相对时间用当前日期推算）
   - `{事件内容}`：要做什么/交付什么
   - `{信号来源}`：对话/电话/妙记/文档/口述
   - `{置信度}`：高（明确日期）/ 中（相对时间）/ 低（模糊表述如"近期"）

2. **列出候选**：用列表形式呈现给用户：
   ```
   检测到 {N} 个时间信号：

   1. 「下周五前完成 xxx」→ 2026-08-01 09:00 [高置信] [来源：对话]
      └ 建议创建：8.01 09:00 提醒
   2. 「每周五下午扫一下群」→ 周期任务 [高置信] [来源：妙记]
      └ 建议创建：每周五 16:00 重复
   3. 「近期整理一下」→ 时间模糊 [低置信] [来源：电话]
      └ 建议忽略或确认时间
   ```

3. **用户确认**：询问「要创建哪些？回复编号即可（如 1,2），或调整时间」
   - 用户回复编号 → 创建对应提醒
   - 用户调整时间 → 按调整后的时间创建
   - 用户说"全部" → 全部创建
   - 用户说"忽略" → 不创建

4. **创建提醒**：对确认的信号调 `schedule_create`（schedule-manager 技能）：
   - 一次性事件 → `category="one_off"`，用具体日期的 cron
   - 周期性任务 → `category="recurring"`，用周期 cron
   - `scene` 跟随原信号场景（work/life）

5. **回复确认**：列出已创建的提醒（job_id、时间、内容），并提示「也可让我后续修改或取消」

**关键约束**：
- **必须先确认再创建**，不要擅自创建提醒（除非用户明确说"自动创建"）
- 时间解析默认 `Asia/Shanghai` 时区
- 模糊时间（近期、尽快）不直接创建，要询问具体时间
- 识别要全面——即便用户主要意图是别的，只要消息/文档里含时间信号就主动列出
- 电话/妙记来源的信号，列出时标注来源，方便用户核对

## 🎯 场景概览

### 场景 A：人员/团队管理

持续收集团队成员工作事件，绩效季汇总评估。

**能力**：手动记录 / 文档分析 / CR 统计 / 绩效汇总 / 任务委派（拆 checkpoint + 创建飞书任务 + 节点提醒）

**信息来源**：手动记录 / 文档分析 / CR 统计 / 群消息提取（定时任务由 schedule-manager 创建）

**详见**：
- `references/people-log.md` — 人员日志格式与写入规则
- `references/workflow.md` — 委派流程 SOP 与 Checkpoint 拆分
- `references/analysis.md` — 文档分析 & CR 分析模板
- `references/review-guide.md` — 绩效评估报告生成

### 场景 B：事情/项目/文档管理

记录项目进展、业务范围、收藏文档、整理沉淀。

**能力**：项目进展追加 / 业务范围维护 / 文档收藏 / 工作沉淀分类整理

### 场景 C：提醒与自动化

主动追踪项目节点、交付截止、例行巡检，到点自动提醒。

**核心机制**：所有提醒创建统一走「定时信号识别」快速路径的确认流程——识别 → 列出候选 → 用户确认 → `schedule_create` → 回复确认。

**典型场景**：
- **项目节点提醒** — 进展中记录的时间节点（如"8.15 完成"）到点前主动提醒
- **交付截止提醒** — 任务 DDL 前 1 天/当天自动提醒
- **例行巡检** — 每日晨间 9:00 扫描 project 进展，发现延期风险预警
- **绩效季提醒** — 绩效季临近时主动提醒收集数据
- **CR 周度汇总** — 每周五 16:00 自动汇总本周团队 MR

**自动建议时机**：在写 project 进展、委派任务、整理沉淀、分析文档时，若内容含明确时间节点，主动列出候选提醒（走定时信号识别流程）。

**首次使用建议**：Agent 主动建议创建：
- 每日晨间（9:00）扫描 project 进展，发现临近节点/已逾期事项
- 每周五（16:00）CR 汇总
- 每季度首月 15 号提醒绩效数据收集

## 📁 数据存储

### 统一走知识库（scene 区分 work/life）

所有数据通过 `knowledge_add` / `knowledge_search` / `knowledge_read` / `knowledge_edit` 读写，`scene` 按 R3 选择。后端切到 Obsidian 时数据自然出现在 vault 的 `work/` 或 `life/` 子目录下。

**条目类型与 tags 约定**（写入时严格按此命名，便于跨条目检索）：

| 类型 | 标题格式 | tags | scene | 写入方式 |
|---|---|---|---|---|
| 人员日志 | `人员日志 - {姓名}` | `["people", "{姓名}"]` | work | knowledge_edit(append) |
| 项目进展 | `项目进展 - {业务名} - {项目名}` | `["project", "{业务名}", "{项目名}"]` | work | knowledge_edit(append) |
| 业务范围 | `业务范围 - {业务名}` | `["scope", "{业务名}"]` | work | knowledge_edit(replace) |
| 文档收藏 | `文档收藏 - {文档标题}` | `["doc", "{业务名}", "{分类}"]` | work/life | knowledge_add |
| 工作沉淀 | `{姓名}工作沉淀 - {分类名}` | `["doc", "people", "{姓名}", "{分类名}"]` | work | knowledge_add |
| CR 周报 | `CR周报 - {业务名} - {YYYY}-W{NN}` | `["cr-report", "{业务名}"]` | work | knowledge_add |
| 绩效草稿 | `绩效草稿 - {YYYY}-Q{N}` | `["review", "{YYYY}-Q{N}"]` | work | knowledge_add / knowledge_edit |
| 个人事项 | `{主题}` | `["personal", "{分类}"]` | life | knowledge_add / knowledge_edit |

**frontmatter 必传场景**：文档收藏、工作沉淀、CR 周报等任何内容派生自外部文档/链接的条目，按 R2 传 `frontmatter={"source": "{原始 URL}"}`。人员日志、项目进展、个人事项等内部记录无需传。

**查询方式**：
- `knowledge_search(query="{姓名}", scene="work")` → 搜该人员的所有记录
- `knowledge_search(query="{业务名} 项目", scene="work")` → 搜该业务的项目进展
- `knowledge_search(query="cr-report {业务名}", scene="work")` → 搜该业务的 CR 报告

### 配置文件（不走知识库）

`~/.ethan/work/team.yaml` — 团队信息（成员列表、业务方向、关注仓库），仍用文件读写。模板见 `templates/team.yaml.example`。

```yaml
# team.yaml 示例
self:
  name: {你的名字}
members:
  - name: {成员名}
    code_username: {git用户名}    # 用于 CR 统计
    open_id: {飞书open_id}        # 用于创建任务/发消息
projects:
  - name: {项目名}
    repo: {仓库路径}
review:
  cycle: quarterly                 # quarterly | monthly
  dimensions: [产出与交付, 技术质量, 主动性与影响力, 成长趋势]
```

### people 日志格式

按人按月按日记录，用 `knowledge_edit`（append）追加到 `人员日志 - {姓名}` 条目。最新月份在上，月份间用 `---` 分隔：

```markdown
# 2026-07

## 07-21
- [亮点] 完成了支付模块联调，性能提升 30%（14:30）
- [问题] 线上 P1 告警，Redis 连接池耗尽（03:15）
- 参加了周会（10:00）

---

# 2026-06

## 06-28
- 修复线上 P1 告警（03:15）
```

**标签约定**：`[亮点]` / `[问题]` / `[进展]` 可选，普通事件不加标签。详见 `references/people-log.md`。

### project 进展格式

用 `knowledge_edit`（append）追加到 `项目进展 - {业务名} - {项目名}` 条目：

```markdown
## 2026-07-21
- xxx 开发中（@小王）
- xxx 已提测（@小李）

## 2026-07-15
- xxx 已完成上线（@小王）

> 路线：7.25 前实现基础功能，8.15 实现 xxx，8.24 完成 xxx
```

- 每次追加一个 `## {YYYY-MM-DD}` 日期标题
- `>` 引用块写路线或 checkpoint（含时间节点，可触发定时信号识别）
- 进展涉及具体人时注明 `（@{姓名}）`

## 🔧 触发识别补充

### 文档分析

用户发送文档链接或说「帮我看看这个文档」时：

1. 读取文档内容
2. 提取亮点（数据/架构/业务价值/风险）
3. 询问归属人
4. 用 `knowledge_edit` 追加到 `人员日志 - {姓名}`，带 `[亮点]` 或 `[问题]` 标签
5. 文档中的时间节点按「定时信号识别」快速路径处理

### CR 分析

用户说「CR 汇总」「代码产出统计」「本周 CR」时，或定时任务触发周度 CR 汇总时：

1. 读取 `team.yaml` 确定业务方向和关注仓库
2. 调 Codebase API 拉取最近一周 MR 数据（按团队成员过滤）
3. 按人统计：MR 数量、代码行数、涉及仓库、关联需求
4. 识别质量问题（P0/P1）和正面信号（见 `references/analysis.md`）
5. 用 `knowledge_add`（scene="work"）创建 CR 周报条目：`CR周报 - {业务名} - {YYYY}-W{NN}`
6. 提取值得记录的事件用 `knowledge_edit` 追加到对应 `人员日志 - {姓名}`（带 `[亮点]` 或 `[问题]` 标签）
7. 回复摘要（关键产出 + 质量趋势）

**定时任务建议**（用户可配置到 `schedule-manager`）：

> 每周五下午对本周团队 MR 做一次 CR 汇总。读取 team.yaml 获取成员和关注仓库列表，调用 Codebase API 拉取本周 MR，按 life-manager 技能的 CR 分析流程生成周报，写入知识库（scene=work），并将关键事件同步到对应人员日志。完成后发送摘要给我。

### 群消息提取

用户说「帮我监控这个群」时：

1. 获取群 chat_id（若已在群内 @bot 则自动取当前群）
2. 询问扫描频率（默认每天 22:00）和时间窗口（默认最近 24 小时）
3. 创建定时任务（通过 `schedule-manager` 的 `schedule_create`），prompt 使用群扫描模板
4. 定时任务触发时按模板步骤拉取消息、识别候选事件、输出去重清单
5. 用户在原渠道回复「入库 1,3,5」确认后用 `knowledge_edit` 追加到对应 `人员日志 - {姓名}`

详见 `references/group-scan-prompt.md`。

## ⚙️ 首次配置

1. 复制 `templates/team.yaml.example` → `~/.ethan/work/team.yaml`，填入团队信息
2. 开始使用——群监控、文档分析、CR 统计均为用户主动触发，无需预配置
3. 首次使用时 Agent 主动建议创建例行巡检任务（见场景 C）

## 🔗 关联技能

| 技能 | 联动方式 |
|---|---|
| `schedule-manager` | 定时任务和时间线管理（任务提醒、周期编排、节点提醒） |
| `code-review` / `bytedance-code-review` | CR 结果记录到 people 日志 |
| `lark-task` | 创建飞书任务和子任务 |
| `lark-im` | 发送提醒消息、识别群聊事件（写入 people 日志） |
| `lark-doc` | 读取文档内容 |
| `lark-minutes` | 从飞书妙记提取信息（电话/会议信号识别的重要来源） |
| `lark-calendar` | 为评审/对齐创建日历事件 |
| `lark-contact` | 解析成员 open_id |

## ⚠️ 约束

- **确认后再创建**：任务拆分、飞书任务、定时提醒的创建必须经用户确认（见定时信号识别流程）
- **不做最终绩效判定**：Agent 只提供汇总和建议，打分由管理者决定
- **隐私边界**：所有记录仅存本地知识库，不上传外部服务
- **客观记录**：people 日志以事实描述为主，避免主观判断词
- **不越权**：Agent 不自行修改 DDL 或取消任务
