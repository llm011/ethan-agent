# 召回、去重与定期整理

## memory 指针（召回的关键）

人物档案存在知识库里，**但知识库不会自动注入上下文**——需要模型主动 `knowledge_search`。问题是：用户说"张三昨天…"时，模型未必意识到"张三"是个值得查档案的熟人。memory 指针就是解决这个的。

### 写指针

首次建档、或身份级信息变化时，`memory_write`：

```
memory_write(
  content="用户的同事张三，支付方向直属下属，做事较真；详细档案见知识库人物-张三",
  memory_type="relationship",
  dimension="relationship.person"
)
```

规则：
- **一句话**，只放身份锚点：谁 + 什么关系 + 一句话画像 + "详细档案见知识库人物-{名字}"
- **不写事件流水**——那是知识库档案的职责，memory 只做"这个人存在"的索引
- 一个人**只维护一条**指针。信息变化时用同样的 `dimension="relationship.person"` 重写一句最新的，admission 管道会 supersede 旧的
- 朋友/家人也写，content 里写清生活关系（"用户的大学室友小林，现在做设计，爱滑雪"）

### 指针如何触发召回

`recall_memory` 是模型按需调用的只读工具。当用户消息涉及某个人名/个人上下文时，模型调 `recall_memory(query="张三")`，命中 `relationship` 域的指针 → 模型据此知道该去 `knowledge_search` 拉全量档案。指针让"聊到熟人 → 捞档案"这条链路稳定触发。

## 按月去重

追加事件前，`knowledge_read` 读档案**当月**已有记录，逐条比对：

| 情况 | 判断 | 处理 |
|---|---|---|
| 完全相同文本 | 精确匹配（忽略标签/时间差异） | 静默跳过，回复"已记录过" |
| 核心动词+对象重叠 | "完成支付联调" vs "搞定支付对接" | 询问用户：合并 / 替换 / 另记？ |
| 带 `[进展]` 标签 | 明确是事件更新 | 直接写入，不问 |
| 完全不同 | — | 直接写入 |

- **核心词提取**：动词（完成/修复/提出/换/搬）+ 对象（支付/告警/工作/家）。两者都重叠才算疑似重复。
- **跨月不去重**：概率低，用户发现可手动改。

### 示例

用户：「张三完成了支付联调」

1. `knowledge_search(query="人物 张三", scene="work")` → 找到 source
2. `knowledge_read` 读当月
3. 比对：
   - 已有 `- 完成支付联调（14:30）` → 完全匹配 → 跳过，回"已记录过"
   - 已有 `- [进展] 支付联调完成` → 核心词重叠但候选是 `[进展]` → 直接写
   - 已有 `- 搞定支付对接（11:00）` → 核心词重叠 → 问"今天已有类似记录'搞定支付对接（11:00）'，合并/替换/另记？"
   - 无相关 → 直接写
4. 按用户回复执行

## 定期整理（配 schedule-manager 定时任务）

日积月累档案会有噪声：重名分裂、时间线碎片、画像过时。建议每月一次低频整理任务，prompt 模板：

```
你是人物志整理助手。遍历知识库中所有 `人物 - *` 档案（scene=work 和 life 都扫），做以下清理：

1. 【重名合并】找出疑似同一个人的多个档案（名字变体、别名），提示用户确认后合并到主名档案，别名记入画像。
2. 【时间线去重】同一档案内，合并核心事件相同的重复条目；保留信息最全的一条。
3. 【画像刷新】从最近 1-2 个月时间线里提炼稳定特征，更新 `## 画像` 段落；过时信息（如已离职/已搬家）move 到时间线并从画像移除。
4. 【指针校准】对有身份级变化的人，用 memory_write 刷新 relationship 指针（一句话，dimension=relationship.person）。
5. 输出整理摘要：处理了哪些人、合并/去重/更新了什么，等用户确认后再落库。

约束：不臆造、不删除用户可能还需要的信息、合并前先征得确认。写入只用 knowledge_edit。
```

配置方式见 `schedule-manager` 技能（category=recurring，如每月 1 号）。
